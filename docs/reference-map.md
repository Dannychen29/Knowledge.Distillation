# 業務知識蒸餾架構：設計與來源對照

本頁供說明 MVP 的設計依據。**研究／方法論說明為何需要這樣處理知識；公開的 Codex／Claude Code 專案說明 Agent 能如何組織部分操作；本 repo 的資料格式和發布門檻是依目的做的工程決定。**「有參考」不等於外部來源驗證了整套框架，更不等於已證明本部門的知識轉移成效。

## 可向主管說明的架構主張

一次先選**一項重要部門任務**，讓 Codex 從文件、訪談、案例及必要的操作觀察取得可定位的證據；整理出規則、判斷理由、例外、交接和具名經驗；由業務參與者核對並用案例走查；發布一份有範圍、來源和缺口的 **Knowledge Release**。Skill、SOP 等是後續按用途選做的應用。這個順序結合 [APQC 的結構化知識轉移](https://www.apqc.org/resource-library/resource/understanding-structured-knowledge-transfer-0/html)、[ACTA 原始研究](https://pubmed.ncbi.nlm.nih.gov/9819578/)、[CommonKADS](https://commonkads.org/basics/) 與 [KCS v6](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/041) 的不同部分；Codex／Claude Code 操作借鏡見 [GitHub 原始檔查核](github-agent-practice.md)。

## 說服力的層級與仍需證明的事

1. **有原始方法或專業實務支撐的問題定義**：為何先找重要任務、追問難以寫進 SOP 的判斷、將知識建模並重用。APQC 是實務指引，ACTA 有原始評估研究，CommonKADS 是知識工程方法，KCS 是服務知識實務；證據性質不同。
2. **有公開 Agent 操作先例的部分步驟**：多來源材料輸入、帶來源的研究綜合、知識捕捉與 Codex 跨次工作。高星是採用度訊號，star 計於整個 repository；[實作參考](github-agent-practice.md) 說明原始檔與限制。
3. **需要本部門試點的整體成效**：目前只有合成資料驗證檔案及發布契約，尚未證明 Codex 能找全重要例外、正確解讀專家理由，或讓接手者獨立處理工作。真實試點應先用一項任務、真人確認、未參與建模的案例及接手者回饋核對這三件事。

因此可說「架構的每個主要環節有可追溯的設計理由」，不可說「整套 Codex 業務蒸餾方法已由文獻或高星專案證實有效」。
